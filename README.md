# 530A Family Contribution Tracker

A static single-page web app for families to track yearly contributions to their children's 530A education savings accounts. Free to host (GitHub Pages), multi-family capable, real-time across all the family's devices.

> This README is the **design spec** for the production rewrite. It is meant to be read end-to-end and signed off before any code lands. Implementation work has not yet started.

---

## What this app does

- Track yearly contributions per child, with a **$5,000 / child / year** hard cap.
- Stop tracking automatically the calendar year a child turns 18.
- Real-time sync across all your family's devices.
- Multiple families can use the same Firebase project with **complete data isolation**.

## Why this design

The original app used Firestore in **Test Mode** for storage. Three forces pushed a redesign:

1. **Test Mode rules expire after 30 days.** After that, reads and writes are blanket-denied by default. We need a rules-driven setup that doesn't auto-lock.
2. **The app needs to deploy on GitHub, free.** GitHub Pages serves only static assets — no Node.js, no Express, no uptime guarantees. That rules out the obvious "self-hosted backend" path.
3. **The repo is public.** Any client-side secret becomes public. Firestore's safety model relies on rules, not key secrecy, so we use production rules plus an email-based access system instead of an invite-only password baked into the front-end.

Decisions locked in:

| Concern | Decision |
|---|---|
| Hosting | GitHub Pages (free, public repo) |
| Backend | Cloud Firestore + Firebase Auth (Email Link / passwordless) |
| Data architecture | Per-family sub-collection isolation |
| Identity | Email (verified via magic link) → membership role |
| Roles | `admin` (family creator) and `viewer` (invited family member) |
| $5,000 enforcement | Loose: per-write ≤ $5,000 in rules, no cumulative server-side check |
| Age constraint | Strict: server compares `birthYear + 18` to contribution year on every write |
| Tier | Spark (free). No Cloud Functions, no Blaze plan. |

## Architecture overview

```
                          GitHub Pages                  Firebase
              ┌─────────────────────────────────┐  ┌──────────────────┐
  Browser ──► │   index.html  js/app.js          │  │ Auth (Email Link) │
              │   js/config.js (build-injected) │  │                  │
              │   js/config.template.js         │  │ Firestore         │
              │   css/style.css                 │  │   families/...    │
              │   firestore.rules (separate)    │  │                  │
              └─────────────────────────────────┘  └──────────────────┘
```

- **Browser → GitHub Pages**: Static assets. Every visitor pulls `index.html`, `app.js`, and the build-generated `config.js`.
- **Browser → Firebase**: All reads and writes run through `firebase.firestore()` calls. The browser authenticates via email magic link.
- **Local dev → Node server**: A small Express dev server (`server.js`) serves the static files on `http://localhost:3000` for development convenience. It is **not** what runs in production.

### Why subcollections (`families/{familyId}/children`) instead of root collections with a `familyId` field

Subcollections give us **physical isolation**. A Firestore query for `families/A/contributions` literally has no path to `families/B/contributions` — the database and the rules reinforce each other. There's no client-side filter that can be forgotten, no chance of a buggy code path accidentally cross-reading data, and rules can use `get(/families/{familyId})` to check membership once per request.

## Data model

### `families/{familyId}`

```json
{
  "familyName": "The Smiths",
  "members": {
    "dad@example.com":     "admin",
    "grandma@example.com": "viewer"
  }
}
```

- `familyName` is a free-form string set on creation.
- `members` is a **map** (not an array) so each email has a role. Allowed values are `"admin"` and `"viewer"`.
- A family's `familyId` is generated by Firestore on first creation.

### `families/{familyId}/children/{childId}`

```json
{
  "name":      "Alice",
  "birthYear": 2015
}
```

`birthYear` is stored as an **integer** (not a `YYYY-MM-DD` string) because rules need to do arithmetic on it.

### `families/{familyId}/contributions/{contributionId}`

```json
{
  "childId":          "child-uuid",
  "amount":           500.00,
  "date":             "2024-10-15",
  "year":             2024,
  "contributorEmail": "grandma@example.com",
  "contributorName":  "Grandma",
  "note":             "Birthday gift"
}
```

- `childId` references the child doc.
- `amount` is a number; rules reject values > 5000 at write time.
- `date` is a `YYYY-MM-DD` string and `year` is its integer prefix — the rules parse `date.split('-')[0]` to compare against `birthYear + 18`.

## Roles

| Action | Admin | Viewer |
|---|---|---|
| Read everything in the family | ✅ | ✅ |
| Create a contribution | ✅ | ✅ |
| Delete a contribution | ✅ | ❌ |
| Add / edit / delete a child profile | ✅ | ❌ |
| Invite a new member as a viewer | ✅ | ❌ |
| Promote a viewer to admin | ✅ | ❌ |
| Demote / remove another admin | ✅ (with UI safeguard) | ❌ |
| Edit the family name | ✅ | ❌ |

The "last admin cannot leave" invariant is enforced by two layers:

- **Rules** prevent an admin from demoting *themselves*: the `update` rule on `families/{familyId}` requires `request.resource.data.members[email] == 'admin'` for the acting admin. If they try to remove or demote their own entry, the rule rejects the write.
- **UI** hides the demote/remove button next to the last remaining admin and shows a red banner so the situation is hard to miss.

> **What the rules cannot enforce.** Firestore rules cannot easily express "this family must always have at least one admin". They enforce "you cannot remove yourself", which stops self-lockouts but not a malicious admin from removing all the *other* admins while keeping themselves as admin. That's accepted as a UI responsibility.

## Authentication flow

### New device, first-ever sign-in

1. Browser loads `index.html`. App checks Firebase Auth state.
2. Unauthenticated → user sees an "Enter your email" screen.
3. App calls `firebase.auth().sendSignInLinkToEmail(email, …)` and stores the email in `localStorage` so the same device can finish sign-in silently.
4. Firebase sends a one-time link via email. Expires after 1 hour.
5. User clicks the link:
   - **Same device** — `firebase.auth().signInWithEmailLink(email_from_localStorage, url)` completes silently.
   - **Different device** — `localStorage` is empty → app prompts "Confirm your email" → user retypes the email → sign-in completes.
6. App fires the routing query: `db.collection('families').where('members.{email}', '!=', null).limit(1).get()`.
   - **0 hits** → "Create Family" wizard.
   - **1+ hits** → pick the first response, set `state.currentFamilyId`, land on dashboard.

### Family creation

- Sign-in without an existing family → "Create Family" wizard.
- User picks a name. App writes:

  ```
  families/{autoId}: { familyName: "...", members: { email: "admin" } }
  ```
- User is now the admin of that family.

### Invite a family member

1. Admin → "Manage Members" tab → enter email → app writes:

   ```
   update families/{familyId}: members[+ 'sister@example.com'] = 'viewer'
   ```
2. Admin tells the new member the URL out-of-band (text, Slack, smoke signal).
3. New member hits the URL, enters their email, magic-link sign-in completes.
4. Routing query returns 1 hit → user lands in the family.

### Admin promotion

Same shape as invite, with role `"admin"`:

```
update families/{familyId}: members['sister@example.com'] = 'admin'
```

Both admins retain their access.

## Firestore security rules

This file ships as `firestore.rules` at the repo root and is deployed via `firebase deploy --only firestore:rules`. It is part of the security boundary — rules are *not* a secret.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isSignedIn() { return request.auth != null; }
    function myEmail()    { return request.auth.token.email; }

    // One `get()` per request against the family doc.
    // Plus one extra `get()` per write that references a child doc
    // (for the age constraint).
    function getFamily(familyId) {
      return get(/databases/$(database)/documents/families/$(familyId));
    }
    function isMember(familyId) {
      return getFamily(familyId).data.members[myEmail()] != null;
    }
    function isAdmin(familyId) {
      return getFamily(familyId).data.members[myEmail()] == 'admin';
    }

    match /families/{familyId} {
      // Anyone signed in who's in this family's `members` map.
      allow read: if isSignedIn() && isMember(familyId);

      // Creation: must include yourself as admin so you immediately own the family.
      allow create: if isSignedIn()
                       && request.resource.data.members[myEmail()] == 'admin';

      // Update: must currently be admin AND must remain admin afterwards.
      // This is what stops an admin from accidentally demoting themselves.
      allow update: if isSignedIn()
                       && isAdmin(familyId)
                       && request.resource.data.members[myEmail()] == 'admin';

      // No hard delete; soft-delete is out of scope of this iteration.
      allow delete: if false;

      match /children/{childId} {
        // IMPORTANT: do not use `allow read, write` here. The shorthand
        // expands to two matching grants (`read` matched on read, `write`
        // matched on create/update/delete), which would OR with the admin
        // grant below and let viewers write children. Split explicitly:
        allow read:  if isSignedIn() && isMember(familyId);
        allow write: if isSignedIn() && isAdmin(familyId);
      }

      match /contributions/{contributionId} {
        allow read: if isSignedIn() && isMember(familyId);

        // Admins and viewers both create. Schema validated here:
        //   - amount is a positive number (per-write rejection if > 5000)
        //   - the date's year is strictly less than the child's birthYear + 18
        // Contributions are append-only; corrections are delete + new write.
        allow create: if isSignedIn()
                        && isMember(familyId)
                        && request.resource.data.amount is number
                        && request.resource.data.amount > 0
                        && request.resource.data.amount <= 5000
                        && int(request.resource.data.date.split('-')[0])
                           < (get(/databases/$(database)/documents/
                                families/$(familyId)/children/
                                $(request.resource.data.childId)).data.birthYear + 18);

        allow update: if false;

        // Only admins can delete a contribution.
        allow delete: if isSignedIn() && isAdmin(familyId);
      }
    }
  }
}
```

**Read-cost note.** Every `get()` inside a rule counts as one database read against the free quota. A small family generates a handful of such reads per session, comfortably inside the 50,000 reads/day free tier.

## Local development

### Prerequisites

- Node 18+
- A Firebase project with Firestore enabled and **Authentication → Sign-in method → Email/Password (link)** enabled.

### One-time setup

```bash
git clone <your-repo>
cd <your-repo>
cp js/config.example.js js/config.js   # fill in real values
# Edit js/config.js with credentials from Firebase Console →
#   Project settings → "Your apps" → Web app config.
# Enable Authentication → Sign-in method → Email/Password (link).
# Enable Firestore in production mode (NOT test mode).
# Add localhost to Firebase Console → Authentication → Authorized domains.
```

### Run locally

```bash
npm install
npm start                # serves on http://localhost:3000
```

`server.js` is a tiny Express app that exposes `/css/`, `/js/`, and `/`. It exists purely for local convenience — it is **not** what runs in production.

```bash
firebase deploy --only firestore:rules
```

You'll need `firebase-tools` (`npm i -g firebase-tools`) and `firebase login` once.

## Deployment to GitHub Pages

### Setting up the project

1. Push the repo to GitHub.
2. In **Settings → Pages**, set the source to the `main` branch / root. Save.
3. Note the URL: `https://<user>.github.io/<repo>/`. Update **Firebase Console → Authentication → Authorized domains** to include this URL.

### Build-time config injection

Because the repo is public, `js/config.js` cannot be checked in. We use a tiny build script that reads from environment variables and writes the file at deploy time.

`scripts/build-config.js` (lives in the repo; reads from env vars):

```js
// Generates js/config.js at deploy time from FIREBASE_CONFIG_JSON env var.
// FAILS the build if the env var is missing or malformed - silently
// continuing would ship a broken app to GitHub Pages.
const fs = require('fs');
const path = require('path');

function fail(msg) { console.error('build-config: ' + msg); process.exit(1); }

const raw = process.env.FIREBASE_CONFIG_JSON;
if (!raw) fail('FIREBASE_CONFIG_JSON env var is required for deploy.');

let parsed;
try { parsed = JSON.parse(raw); }
catch (e) { fail('FIREBASE_CONFIG_JSON is not valid JSON: ' + e.message); }

// Validate the parsed config has the fields we actually need at runtime.
const required = ['apiKey', 'projectId', 'authDomain', 'appId'];
const missing = required.filter(k => typeof parsed[k] !== 'string' || !parsed[k]);
if (missing.length) fail('FIREBASE_CONFIG_JSON is missing fields: ' + missing.join(', '));

const minified = JSON.stringify(parsed);
fs.mkdirSync(path.join(__dirname, '..', 'js'), { recursive: true });
fs.writeFileSync(
  path.join(__dirname, '..', 'js', 'config.js'),
  `// GENERATED by scripts/build-config.js at deploy time. Do not edit.\nwindow.firebaseConfig = ${minified};\n`
);
console.log('Wrote js/config.js');
```

`package.json` exposes it as `npm run build:config`.

## Migration from existing flat Test-Mode data

The current production has data in the **root** collections `/children` and `/contributions` in Test Mode. The new model moves it under `families/{familyId}/...`. Run once.

### One-shot migration script

`scripts/migrate-to-families.js` (lives in the repo; runs locally with admin SDK credentials):

```js
// Run with:
//   GOOGLE_APPLICATION_CREDENTIALS=service-account.json \
//   node scripts/migrate-to-families.js
//
// Two safety features beyond a naive migration:
//   - Validates placeholders and date formats before any write.
//   - Uses Firestore BatchedWriter for atomic per-doc move+delete, so the
//     script never leaves a half-migrated doc behind if it crashes mid-run.
const admin = require('firebase-admin');
admin.initializeApp();
const db   = admin.firestore();

const ADMIN_EMAIL = 'YOUR_EMAIL_HERE';   // <-- edit before running
const FAMILY_ID   = 'YOUR_FAMILY_ID';    // <-- edit before running

const YEAR = (s, field) => {
  if (typeof s !== 'string' || !/^\d{4}-\d{2}-\d{2}$/.test(s)) {
    throw new Error(`${field} "${s}" is not YYYY-MM-DD; refusing to migrate.`);
  }
  const y = parseInt(s.slice(0, 4), 10);
  if (y < 1900 || y > 2100) {
    throw new Error(`${field} year ${y} is out of plausible range; refusing.`);
  }
  return y;
};

(async () => {
  if (ADMIN_EMAIL.includes('YOUR_') || FAMILY_ID.includes('YOUR_')) {
    throw new Error('Edit ADMIN_EMAIL and FAMILY_ID before running this script.');
  }
  console.log(`Migrating into families/${FAMILY_ID} with admin ${ADMIN_EMAIL}.`);

  // 1. Create the family doc with you as admin.
  await db.collection('families').doc(FAMILY_ID).set({
    familyName: 'My Family',
    members: { [ADMIN_EMAIL]: 'admin' },
  });

  // 2. Migrate children with field validation, in 400-doc batches.
  const childrenSnap = await db.collection('children').get();
  let i = 0;
  while (i < childrenSnap.docs.length) {
    const batch = db.batch();
    childrenSnap.docs.slice(i, i + 400).forEach(doc => {
      const data = doc.data();
      const docRef = db.collection('families').doc(FAMILY_ID)
                       .collection('children').doc(doc.id);
      batch.set(docRef, {
        name: data.name,
        birthYear: YEAR(data.birthDate, `children/${doc.id}.birthDate`),
      });
      batch.delete(doc.ref);
    });
    await batch.commit();
    i += 400;
  }

  // 3. Migrate contributions verbatim, plus a `year` integer field.
  const contribSnap = await db.collection('contributions').get();
  i = 0;
  while (i < contribSnap.docs.length) {
    const batch = db.batch();
    contribSnap.docs.slice(i, i + 400).forEach(doc => {
      const data = doc.data();
      const docRef = db.collection('families').doc(FAMILY_ID)
                       .collection('contributions').doc(doc.id);
      batch.set(docRef, { ...data, year: YEAR(data.date, `contributions/${doc.id}.date`) });
      batch.delete(doc.ref);
    });
    await batch.commit();
    i += 400;
  }

  console.log(`Migration complete. ${childrenSnap.size} children, ${contribSnap.size} contributions moved.`);
  process.exit(0);
})().catch(err => {
  console.error('Migration failed:', err);
  process.exit(1);
});
```

### Migration checklist

1. **Back up the Firestore data** (Firestore → Export in the Console).
2. `npm i firebase-admin` *inside* the migration script folder (don't pollute the app's `package.json`).
3. Generate a service-account key (**Firebase Console → Project settings → Service accounts → Generate new private key**) and use it locally via `GOOGLE_APPLICATION_CREDENTIALS=...`.
4. Edit the script with your admin email and chosen `familyId`.
5. Run the script. Verify by signing into your account in the browser and confirming access.
6. Hard-delete the root collections if you intend to lock rules down (the rule file above has no `match /children` clause at root, so they're denied by default — but cleanup saves egress quota).
7. Deploy the new `firestore.rules` **last**, only after verifying your access.

## Known limitations / threat model

Documented carefully because the data is real (children's names + financial contributions).

### Loose $5,000 cap

The rules reject any single contributing write over $5,000. They do **not** reject ten $1,000 writes in the same year. The cumulative yearly cap is enforced **client-side only** in the live validation. A motivated attacker who already has read+write access to your family could bypass the yearly cap by splitting writes.

**Mitigation**: the rules only grant read+write to emails in the `members` map; that's the real security boundary. We accept that the cumulative limit is a soft UX feature, not a security boundary.

### Age constraint is strict

`year < birthYear + 18` is enforced server-side per write. Verified to work without Cloud Functions.

### UI safeguard for "last admin"

Firestore rules cannot easily enforce "this family must always have at least one admin". They enforce "you cannot demote yourself", which stops self-lockouts but not a malicious admin from removing all the **other** admins. The UI mitigates the obvious accident: the remove button next to the last admin is disabled and a red banner prompts the user to invite another admin first.

### Public repo + GitHub Pages

The Firebase web API key ships inside the browser bundle. This is unavoidable for any Firebase web app — Firestore's safety model relies on the rules, not on key secrecy. We still inject `config.js` at build time rather than committing it, because it keeps the repo clean and makes rotation trivial.

### Best-effort email magic-link UX

- Magic links expire after 1 hour.
- If the user opens the link on a different device than they requested the link from, the app can't quietly fill their email and instead asks them to retype it. This is a Firebase Auth limitation, not our bug.
- Spam filters sometimes drop the email. Recommend asking users to check junk.

### Multi-family per user is supported in the data model, not the UX

The data model supports a single email being a member of multiple families. The UI assumes a 1:1 relationship. If a signed-in user's email appears in two families, the routing query returns two results; the app picks the first. **Future work**: a small "Switch Family" dropdown in the header.

### Single-family UX assumption

This app assumes household size 2–7 relatives. It does not model hierarchical roles ("custodial parent", "ex-spouse"). Anyone in `members` is treated as admin-or-viewer. If your family structure needs more granularity, the rules should grow incrementally.

## Future work

- **Strict $5,000 cap (cumulative across the year).** Requires a Cloud Function + Firestore transaction; needs Blaze plan. Worth it for a high-trust family.
- **Switch-family dropdown** in the header when an email is in multiple families.
- **Contributor email column** in the contribution table so you can audit who logged what.
- **Soft-delete** for families and children (`deletedAt` field; rules deny reads on deleted-but-still-present docs).
- **Backup workflow** — daily export of `families/*` to a Cloud Storage bucket, triggered by a scheduled GitHub Actions cron.
- **Audit logging** — a separate `events/{eventId}` log collection written from the client.
- **PWA / offline-first** — cache last-known state with a service worker so the app is usable when Firestore is unreachable.
